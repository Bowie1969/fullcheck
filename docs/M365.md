# FullCheck M365 / Entra ID module (`fullcheck m365`) v0.2

The external cloud-tenant sibling of FullCheck. Same spine (Action, Dispatcher,
ApprovalGate, Evidence) — **imported, not forked** — so cloud work can't drift
away from the safety rules the rest of the tool enforces. What changes is that a
unit of work is an HTTP call to Microsoft's shared endpoints rather than a
subprocess, and what the blast-radius tiers mean for a cloud tenant.

## Scope semantics (read this first)

M365 recon talks to Microsoft's **shared** endpoints —
`login.microsoftonline.com`, `autodiscover-s.outlook.com`,
`graph.microsoft.com` — **never** to infrastructure the client controls. The
thing being *assessed*, and therefore the Dispatcher `target`, is the client's
**tenant**, identified by one of its verified domains (e.g. `contoso.com`).

So `scope.yaml` lists the client **domain(s)**; the Dispatcher scope/ceiling/rate
check runs against that domain exactly as it does for any other target. Requests
egress to Microsoft; authorization is checked against the tenant you were hired
to look at. The absolute rule still holds: a domain enters `scope.yaml` only
after a signed written authorization for that tenant is on file.

## Runtime

Runs from the **ParrotOS x86 laptop** (this repo), same as the external tool.
It's pure HTTP, so no pentest binaries are involved — but authenticated Graph
reads need `msal`, an **optional** dependency:

```bash
pip install -e '.[m365]'
```

Everything else (unauthenticated recon, analyze, the offline smoke test) works
without it — `msal` is imported lazily and only the `scan` verb needs it.

## The tier model for a cloud tenant

| Tier | Cloud meaning | Runs how |
|------|---------------|----------|
| PASSIVE | unauth tenant metadata: OpenID config, user-realm/federation, tenant domains, branding, DNS posture, SharePoint/Teams existence | no gate |
| PROBE | account-validity enumeration via `GetCredentialType` — **no password is ever sent** (no lockout), but logged/alertable | ceiling-gated + politeness delay |
| SCAN | authenticated Graph **reads**: CA policies, MFA registration, privileged roles, app/SP surface, ID Protection, … | ceiling-gated, needs an app registration |
| EXPLOIT / POST_EXPLOIT | password spray, MFA-fatigue, illicit consent, token replay | **FLOOR** — always human-confirmed |

Recon (PASSIVE/PROBE) and SCAN never send a credential or attempt a sign-in.
Anything that does is FLOOR-class active work (see below), routed through the
same human `ApprovalGate` the rest of FullCheck uses. There is no auto path for
it, ever.

## Active techniques are FLOOR-only (and ship as stubs)

Password spray (Entra Smart Lockout, sign-in alerts), MFA-fatigue push-bombing
(harasses a real user), illicit OAuth consent (phishes a real user), and token
replay (post-compromise) all carry real lockout / alerting / user-impact risk.
Every one is **FLOOR**: it runs ONLY behind `ceiling: exploit` in `scope.yaml`
**and** a per-action human confirm token — the existing
`attack → approve → exploit-run` path.

They currently ship as **stubs** (`stub = True`): the gate and the intent are
wired, but no live tool invocation is, so `attack` refuses them until an operator
deliberately implements `_build` against an authorized tool. That is the point —
ship the safety gate before the weapon. See them:

```bash
fullcheck m365 catalog
```

## The Graph app registration (for `scan`)

The SCAN tier authenticates to Microsoft Graph and does **read-only GETs**. Create
a dedicated app registration in the client tenant with **read-only** permissions.
A missing scope isn't fatal — it surfaces as one skipped check (the harness
tolerates 403), so grant what the engagement needs and no more.

A consolidated read-only application-permission set that covers the built-in
checks (`src/fullcheck/m365/graph_checks.py`):

| Graph permission | Covers |
|------------------|--------|
| `Directory.Read.All` | organization, domains, users, groups, devices, directory roles, SPs |
| `Policy.Read.All` | Conditional Access + authorization/consent/auth-method/named-location/cross-tenant policies |
| `Application.Read.All` | app registrations + service principals detail |
| `AuditLog.Read.All` | MFA registration report, directory audits, `signInActivity` on users |
| `RoleManagement.Read.Directory` | PIM eligible role assignments, role templates |
| `DelegatedPermissionGrant.Read.All` | OAuth2 delegated permission grants |
| `CrossTenantInformation.Read.All` | cross-tenant access default policy |
| `IdentityRiskyUser.Read.All`, `IdentityRiskEvent.Read.All` | Entra ID Protection (needs Entra ID **P2**) |

Grant admin consent for the application permissions. Each `GraphCheck` records
the scope it needs in its `scope=` field, which also shows up in the report.

### Credentials

Creds are **never** read from `scope.yaml` (that file is about authorization, not
secrets). They resolve in this order:

1. environment: `M365_TENANT_ID`, `M365_CLIENT_ID`, `M365_CLIENT_SECRET`
2. a git-ignored per-engagement file `engagements/<client>/m365_app.json`:
   ```json
   {"tenant_id": "...", "client_id": "...", "client_secret": "..."}
   ```

Provide the secret → **client-credentials** flow (app-only, unattended). Omit the
secret → **device-code** flow: the operator visits the printed URL and signs in
with a delegated read account (useful when you don't want a standing app secret).

## Typical flow

```bash
# scope.yaml lists the tenant domain; ceiling gates the tier (scan needs `scan`)
fullcheck new contoso --auth-ref M365-CONTOSO-20260901-001

# 1. unauthenticated recon (PASSIVE) + optional user-enum (PROBE)
fullcheck m365 recon contoso -d contoso.com \
    --auth-ref M365-CONTOSO-20260901-001 --users candidates.txt

# 2. authenticated Graph reads (SCAN) — needs the app registration above
fullcheck m365 scan contoso -d contoso.com --auth-ref M365-CONTOSO-20260901-001

# 3. deterministic findings from the recon/scan artifacts (no LLM)
fullcheck m365 analyze contoso -d contoso.com

# 4. render the findings into m365_report.md (same template as the external tool)
fullcheck m365 report contoso -d contoso.com --auth-ref M365-CONTOSO-20260901-001
```

Active work (only if the engagement ceiling is `exploit` and a technique is
wired) reuses the shared HITL exploit path:

```bash
fullcheck m365 attack contoso -t m365-password-spray -d contoso.com \
    --auth-ref M365-CONTOSO-20260901-001 --param users=valid.txt
#   -> parked for approval; you confirm the exact command:
fullcheck approve     contoso --auth-ref M365-CONTOSO-20260901-001
fullcheck exploit-run contoso --auth-ref M365-CONTOSO-20260901-001
```

Every step — recon, scan, or attack — passes the Dispatcher (scope + ceiling +
rate on the tenant domain) and writes the hashed evidence chain tied to the auth
reference. `analyze` findings each cite the `raw/…` artifact that justifies them.

## Analyze is deterministic, not LLM

For structured Graph data FullCheck doesn't involve the LLM at all: findings come
from explicit `@rule` functions over the evidence artifacts
(`src/fullcheck/m365/analyze_rules.py`), each asserting only what the artifact
shows and citing it. That keeps every M365 finding auditable and reproducible.

## Adding coverage

- **Recon probe** — subclass `M365Probe` in `m365/recon.py`, `name` prefixed
  `m365-`, set `blast_radius` (PASSIVE for pure unauth metadata; PROBE only for
  account-validity/auth-looking traffic — never authenticated Graph or a
  credential), defensive `collect()` (catch per-request errors into the dict),
  `@register_probe`. No password, no sign-in.
- **Graph check** — append a `register_check(GraphCheck(...))` in
  `m365/graph_checks.py`. Must be a **GET**; note the scope it needs.
- **Finding rule** — append a small pure `@rule` in `m365/analyze_rules.py`; set
  `evidence_artifact` to the citing artifact.
- **Active technique** — subclass `M365Technique` in `m365/techniques.py`,
  `blast_radius` EXPLOIT or POST_EXPLOIT, a one-line `risk`, and either a real
  `_build` or `stub = True`. FLOOR-only by policy — never add an auto path.

Then add a matching assertion to `scripts/m365_smoke_test.py` and keep it green:

```bash
python scripts/m365_smoke_test.py   # offline, no network, no msal needed
```
